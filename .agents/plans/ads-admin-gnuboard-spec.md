# 그누보드5 동영상 광고 관리 기능 명세

작성: ads-admin-designer, 2026-10-20. 상태: 기획 명세 초안. 공통 계약은 오케스트레이터가 C1에서 확정한다.
관계: 독립 설치용 전체 기능은 `ads-admin-v2-spec.md`(이하 v2)를 따른다. **그누보드5 연동판은 이 문서를 따른다.** 이 문서에 없는 재생·이벤트·보안 규칙은 v2와 C0(`ads-contract-v1.md`)를 따른다.

## 1. 개요

그누보드5판은 v2보다 간략하게 구현한다. 핵심은 **1:1 문의(QA) 구조를 본뜬 "광고 요청" 기능**이다.

```
회원(광고주) ── 광고 요청서 작성 ──▶ 관리자 검토 ──▶ 승인 시 소재·집행 자동 생성 ──▶ 재생 시 노출
      ▲                                │  보완 요청 / 반려                            │
      └──── 쪽지 알림 · 요청 글에서 진행 상태와 성과 조회 ◀────────────────────────────┘
```

## 2. 인터뷰 결정

| ID | 항목 | 결정 |
| --- | --- | --- |
| G01 | 구현 방식 | `g5_qa_*`의 구조와 화면 흐름(목록·작성·보기·답변)을 본뜬 **별도 모듈**. 광고 제품 테이블(`g5ads_` 등 설정 접두어)과 별도 페이지를 쓰며 코어와 기존 1:1문의는 수정하지 않는다 |
| G02 | 요청자 | 로그인 회원만. 회원 = 광고주 |
| G03 | 요청 항목 | 소재 파일/URL, 희망 기간·위치, 희망 노출 수·예산 메모 |
| G04 | 승인 후 | 요청 승인 시 소재와 집행을 자동 생성. 요청자는 같은 글에서 진행 상태와 성과를 조회 |
| G05 | 단순화 | 역할·승인 단계 제거, 광고주·캠페인 계층 축소, 점유율·페이싱 단순화, 대시보드·다축 리포트 제외 |
| G06 | 요청 상태 | 접수 → 검토 → (보완 요청) → 승인/반려 → 집행 → 종료 |
| G07 | 승인 후 요청자 권한 | 조회만. 일시중지·소재 교체·CSV는 제공하지 않는다 |
| G08 | 알림 | 그누보드 쪽지 |

## 3. v2 대비 차이

| v2 기능 | 그누보드5판 |
| --- | --- |
| 편집자·승인자 역할, 게시 승인 | 없음. 그누보드 관리자 권한 하나로 처리한다. **요청 승인이 곧 집행 승인**이다 |
| 광고주 → 캠페인 → 집행 | 회원 1명 = 광고주, 요청 1건 = 집행 1개(캠페인은 내부적으로 1:1 자동 생성) |
| 기간제 점유율, 보장 균등 페이싱 | 없음. 기간 내 가중치 로테이션, 희망 노출 수 도달 시 중지 |
| 소재 심사 상태 | 요청 승인에 포함한다. 관리자가 직접 등록한 소재는 바로 사용한다 |
| 지면 편성 승인 | 없음. 관리자가 초안 저장 후 바로 게시(v1 흐름) |
| 대시보드, 다축 리포트, 광고주 링크 | 없음. 요청별 성과 + 기존 통계·CSV에 요청 필터 추가 |
| 노출(impression) 이벤트, 노출 인정 시간 설정 | **유지**. 희망 노출 수 차감 기준이다(v2 §6) |
| 빈 슬롯 처리, 세션 내 중복 방지 | 유지(v2 §5.2) |

## 4. 사용자와 권한

- **요청자:** 로그인 회원이며 설정한 최소 레벨(기본 2) 이상이어야 한다. 자기 요청만 목록·보기에서 조회한다(QA의 `mb_id` 조건과 동일한 원칙). 비회원은 로그인 화면으로 보낸다.
- **관리자:** 최고관리자 또는 광고 관리 메뉴(예: `300950`)에 쓰기(w) 권한이 있는 회원. 모든 요청 조회, 검토·승인·반려·보완 요청, 집행 중단, 하우스 광고·지면 편성 관리. 읽기(r) 권한만 있으면 조회만 한다.
- 권한 판정은 v1 그누보드 어댑터(`common.php` 로드, `auth_check_menu`, `check_admin_token`)를 재사용한다. 요청자 화면의 쓰기는 그누보드 회원 세션과 CSRF 토큰으로 보호한다.

## 5. 광고 요청서

| 필드 | 필수 | 규칙 |
| --- | --- | --- |
| 제목 | ✓ | 1–255자 |
| 광고 이름 | ✓ | 1–200자. 승인 시 소재 이름이 된다 |
| 소재 | ✓ | 파일 업로드 또는 URL 중 하나. MP4/WebM/JPEG/PNG/WebP/GIF. 업로드 제한·MIME 검사·저장 방식은 v1 업로드 규칙을 따르며 그누보드 `data/` 폴더는 쓰지 않는다. 요청당 소재는 최대 2개(QA의 첨부 2개 구조) |
| 대체텍스트 | 이미지면 ✓ | 1000자 이내 |
| 클릭 URL | | http(s) URL |
| 희망 기간 | ✓ | 시작일 ≤ 종료일, 시작일은 오늘 이후 |
| 희망 위치 | ✓ | 프리롤 / 미드롤 / 포스트롤 중 1개 이상 |
| 희망 노출 수 | | 양의 정수. 비우면 기간 동안 무제한 |
| 예산 메모 | | 텍스트 500자. **결제·정산은 범위 밖**이며 참고 정보일 뿐이다 |
| 요청 내용 | ✓ | 설명. 편집기 사용 여부는 설정(QA의 `qa_use_editor`와 같은 방식) |

- 연락처는 회원 정보에서 가져온다. 요청서에서 별도로 받지 않는다.
- 노출 게시판은 요청자가 고르지 않는다. 관리자가 승인할 때 정한다.

## 6. 요청 상태

```
접수 ─(관리자 열람/검토 시작)─▶ 검토 ─┬─ 보완 요청 ─(요청자 수정·재제출)─▶ 접수
                                       ├─ 반려(사유 필수, 종결)
                                       └─ 승인 ─▶ 집행 예정 ─(시작일)─▶ 집행 ─▶ 종료
                                                                              (기간 종료 / 노출 수 도달 / 관리자 중단)
```

- 요청자는 **접수·보완 요청 상태에서만** 요청서를 수정하거나 취소할 수 있다(QA에서 답변 전에만 수정할 수 있는 것과 같은 원칙). 승인 후에는 조회만 한다(G07).
- "집행 예정·집행·종료"는 생성된 집행의 기간·목표·중단 여부로부터 계산한다. 종료 사유를 함께 표시한다.
- 모든 상태 변경은 요청의 처리 기록(§7)에 남는다.

## 7. 처리 기록과 답변

QA의 질문/답변(`qa_type`, `qa_parent`) 구조를 본떠 요청 1건에 처리 기록 목록을 붙인다.

- 기록 종류: 관리자 답변, 상태 변경(자동 문구), 요청자 재제출 메모.
- 보완 요청과 반려는 관리자 답변이 반드시 함께 있어야 한다.
- 요청자는 보완 요청 상태에서 재제출하면서 메모를 남길 수 있다. 그 외 추가 문의는 받지 않는다.
- 첨부: 관리자 답변에는 파일을 첨부하지 않는다. 필요하면 링크로 안내한다.

## 8. 승인 시 자동 생성

관리자는 승인 화면에서 요청 값을 확인하고 **최종 집행 값을 조정**한 뒤 승인한다.

| 최종 값 | 기본값 |
| --- | --- |
| 집행 기간 | 희망 기간 |
| 위치 | 희망 위치 |
| 노출 게시판 | 전체 게시판. 게시판 다중 선택(포함) 가능 |
| 목표 노출 수 | 희망 노출 수(비어 있으면 무제한) |
| 스킵 | 설정의 기본값(예: 5초 후 스킵) |
| 이미지 표시 시간 | 설정의 기본값 |
| 가중치 | 1 |

승인하면 한 트랜잭션에서 다음을 만든다: 소재(요청 소재 → 승인된 소재 버전), 광고주(회원 ID 연결, 없으면 생성), 캠페인 1개, 집행 1개. 요청에는 생성된 집행 ID를 연결한다. 이후 소재 교체·기간 변경은 관리자만 할 수 있으며 처리 기록에 남긴다.

## 9. 재생 시 선택(단순화)

```
슬롯마다:
1) 요청 집행: 승인됨 · 기간 내 · 위치 일치 · 게시판 일치 · 목표 미도달 · 중단 아님 → 가중치 무작위
2) 없으면 하우스(관리자가 직접 등록한 광고) → 가중치 무작위
3) 없으면 빈 슬롯(광고 없이 진행, 통계에 기록)
```

- 요청 집행이 하우스보다 우선한다. 페이싱이 없으므로 기간 초반에 노출이 몰릴 수 있다. 요청자에게 "희망 노출 수 도달 시 조기 종료"를 안내한다.
- 목표 도달 판정, 이미 발급된 세션의 초과 노출, 일시중지의 스냅샷 고정 규칙은 v2 §5.3–5.4와 같다.
- 지면 편성(사이트 → 게시판 → 분류 → 영상, 구간별 슬롯 수)은 v2 §4.4 구조를 쓰되 승인 없이 관리자가 바로 게시한다.

## 10. 화면

### 10.1 요청자 화면(사이트 프런트)

QA 화면처럼 사이트 테마의 head/tail 안에 표시한다. 스킨은 PC·모바일 기본 스킨을 하나씩 제공한다.

- **내 광고 요청 목록:** 번호, 제목, 상태 배지, 희망 기간, 등록일. 상태 필터와 페이지 이동. 상단에 설정의 안내 문구를 표시한다.
- **요청서 작성·수정:** §5 필드. 업로드 제한과 지원 형식을 표시한다. 제출 전 소재 미리보기(이미지 썸네일, 영상 재생)를 제공한다.
- **요청 보기:** 요청 내용, 상태 단계 표시줄, 처리 기록(답변·상태 변경), 승인 후 **성과 카드**(노출, 완료, 클릭, 클릭률, 목표 대비 진도) + 일별 표. 성과는 사이트 시간대 기준이며 늦게 도착한 기록으로 수치가 바뀔 수 있다는 안내를 붙인다.
- 접수·보완 요청 상태에서만 수정·취소 버튼을 표시한다.

### 10.2 관리자 화면(별도 팝업 창)

광고 관리는 그누보드 관리자 레이아웃(상단 바·왼쪽 메뉴) 밖의 별도 팝업 창에서 연다. 그누보드 관리자 메뉴에는 이 팝업을 여는 진입 링크 하나만 둔다.

- **팝업 GNB:** 창 맨 위에 둔다. 왼쪽부터 "[사이트 이름] 광고 관리" · 광고 요청 · 하우스 광고 · 지면 편성 · 통계 · 설정, 오른쪽에 사이트 보기 · 관리자 · 창 닫기 순서다(계약 `ads-admin-app-contract.md` 3절 gnuboard 행과 같다). 사이트 이름이 없으면 "광고 관리"만 쓴다. 창 닫기는 `window.opener`가 있을 때만 보인다. 960px 미만에서는 메뉴가 두 번째 줄로 내려간다.
- 아래 각 화면은 이 GNB 메뉴로 오간다.

- **광고 요청 관리:** 전체 요청 목록. 상태·기간·회원 검색, 미처리(접수) 건수 배지. 행에서 상세로 이동한다.
- **요청 상세:** 요청 내용, 소재 미리보기, 처리 기록. 동작: 검토 시작, 답변, 보완 요청, 반려, 승인(§8 최종 값 패널), 집행 중단. 승인 후에는 집행 성과와 집행 수정(기간·게시판·목표·소재 교체)을 보여 준다.
- **하우스 광고:** 관리자가 직접 소재를 등록하고 기간·위치·게시판·가중치를 지정한다(요청 없이 바로 집행).
- **지면 편성:** v1 편성 화면 + 구간별 슬롯 수.
- **통계:** v1 통계 화면에 요청(집행) 필터를 추가하고 노출·채움률 열을 추가한다. CSV 유지.
- **설정:** 요청 기능 사용 여부, 요청 가능 최소 회원 레벨, 안내 문구, 편집기 사용, 알림 수신 관리자 회원 ID, 업로드 제한, 기본 스킵·이미지 표시 시간, 노출 인정 시간(기본 영상 2초·이미지 1초).

## 11. 쪽지 알림

| 시점 | 수신자 | 내용 |
| --- | --- | --- |
| 새 요청 접수, 재제출 | 설정한 관리자(기본 최고관리자) | 요청 제목과 관리자 상세 링크 |
| 보완 요청, 반려, 승인, 집행 시작, 종료 | 요청자 | 상태와 요청 보기 링크 |

- 발신자는 설정한 관리자 회원 ID다. 쪽지 발송 포인트는 차감하지 않는다.
- **위험:** 쪽지는 호스트 테이블(`g5_memo` INSERT, `g5_member.mb_memo_call` UPDATE)에 쓰는 작업이다. 현재 README의 "제품 테이블만 쓴다"는 원칙과 충돌하며, 메모 테이블 컬럼은 그누보드 버전마다 다르다(확인한 로컬 소스는 `me_id, me_recv_mb_id, me_send_mb_id, me_send_datetime, me_memo`만 사용). 호스트 어댑터에서 스키마를 감지해 발송하고, 실패해도 요청 처리는 성공시키며 처리 기록에 "알림 실패"로 남기는 방식을 제안한다(GO1).

## 12. 저장 구조(초안)

- `requests`: 요청 ID, 회원 ID, 상태, 제목, 요청서 문서(JSON), 생성된 집행 ID, 생성·수정 시각.
- `request_logs`: 요청 ID, 작성자 회원 ID, 관리자 여부, 종류(answer/status/resubmit), 본문, 이전·다음 상태, 시각.
- 요청 소재 파일은 v1 업로드 저장소를 쓰며 요청 ID에 연결한다. 승인 전 파일은 소재 버전이 아니다.
- 소재·집행·캠페인·광고주·슬롯 결과·impression은 v2 테이블을 **단순화 모드로 공유**한다(tier는 `request`/`house`). 독립 설치판과 코드를 분기하지 않기 위한 제안이다(GO2).

## 13. 1차 인수 기준

- 회원 A는 회원 B의 요청을 목록·보기·수정·성과 API 어디서도 볼 수 없다. 비회원과 레벨 미달 회원은 요청할 수 없다.
- 승인 1회로 소재·집행이 생성되고 다음 발급 세션부터 노출 후보가 된다. 반려·보완 요청 건은 노출되지 않는다.
- 승인 후 요청자의 수정·취소 요청은 서버에서 거부된다.
- 희망 노출 수에 도달하면 신규 선택에서 제외되고 상태가 "종료(노출 수 도달)"가 된다.
- 요청 집행 → 하우스 → 빈 슬롯 순서를 고정 시드 테스트로 증명한다.
- 쪽지는 실제 그누보드 격리 환경에서 발송·수신을 확인한다. 실패 시 요청 처리가 롤백되지 않는다.
- 단위 테스트, HTTP·DB, 브라우저, 실제 그누보드 로그인·메뉴 권한은 별도 증거로 보고한다.

## 14. 범위 밖

결제·포인트 차감·정산, 요청자의 일시중지·소재 교체·CSV, 비회원 요청, 기간제 점유율과 균등 페이싱, 편집자·승인자 역할, 대시보드·다축 리포트·광고주 링크, 영카트 주문 연동.
